# 部署与维护交接

## 迁移到普通服务器

1. 在开发机用 Node.js 24 执行 `npm ci`、`npm run verify`。
2. 将 `dist/` 的全部内容原样上传。必须同时包含 `index.html`、`assets/` 和 `media/`，不能只上传 HTML。
3. 将这些文件作为网站根目录，或放进已有网站的子目录（如 `/travel/`）。访问子目录时保留末尾 `/`。
4. 使用 HTTPS。图片、CSS、JavaScript 均从同一站点加载；复制功能在浏览器不给剪贴板权限时会提供手动复制提示。
5. 正式验收首页、两条路线、地图站点、问卷结果、护照下载、画廊、咨询清单，以及预订／支付演示的成功、失败、取消与返回路径，再交付域名。

这是标准静态部署，方式与 [Vite 官方部署说明](https://vite.dev/guide/static-deploy.html) 一致。`base: './'` 使用相对资源路径。对 Node.js 的要求仅发生在开发/构建环节，运行网站的服务器无需安装 Node.js。

部署不依赖飞书账号、app_id、环境变量、接口代理、对象存储外链或服务端代码。`docs/asset-manifest.json` 中保留的旧平台地址只用于素材追溯，不进入网页构建产物。

## 日常修改

- 路线数据在 `src/wufang/model.mjs`。`days` 的第一项是单独抵达日，因此长度为 `daysCount + 1`；地图的 `day` 索引必须指向真实行程。
- 更换图片：替换 `public/media/` 的同名文件，或添加文件后修改 `model.mjs` 与相应 HTML 图片引用。保持描述与画面相符。若文件变化，重新生成/更新素材校验清单及验收证据。
- 固定路线卡片和咨询选择框在 `index.html`，新增路线时应同步修改，不能只改数据模型。
- 改视觉时优先在 `styles-tibet.css` 调整；`styles.css`、`booking.css` 提供现有控件基础样式。`styles-v2.css` 是未加载的历史主题，不要误改该文件。
- 每次改完运行 `npm run verify`，再做一次手机和桌面端的浏览器验收。

## 接后端时的接口边界

当前 `buildInquiry()` 生成纯文本清单，页面明确说明未发送。`booking.mjs` 和 `booking-ui.js` 提供独立的预订与支付演示，金额、订单与状态均由前端模拟，不能作为真实交易依据。接入真实支付时，价格、库存、订单创建、支付签名、回调验签与最终状态必须由服务端负责；不能把浏览器里的“模拟成功”结果当作付款证据。具体边界见 `BOOKING-DEMO.md`。

等品牌确认正式客服与业务流程后，再决定连接咨询接口还是客服入口。接入成功前不要移除演示标识，或把模拟状态改成真实“预订成功”。现有源码不含密钥、用户数据库或 API 访问凭证。

## 从 H5 继续到小程序

如果只是保留网页版，可以继续部署这份工程。如果要使用微信原生页面，需要选择小程序框架后迁移界面：`model.mjs` 的路线/问卷/咨询生成函数可复用；`app.js` 的 DOM、dialog、History、localStorage、Canvas 下载等调用需要分别替换成小程序能力。H5 已完成不等于小程序已交付。

## 甲方待补内容

公开团期与余位、最终价格、费用包含/不包含、退改规则、正式客服微信或二维码，以及最终住宿/车辆/领队资料。当前页面保留“参考/待确认”说明，不能把这份前端包当作已上线的订单系统。
